# ByteCodeVM — план декомпиляции обфускации «чистый байткод»

Этот файл — будущий план для самого жёсткого сценария: обфускац-«франкенштейн»,
где у классов **нет** ни внятных имён, ни типов, ни дебаг-инфы (`LocalVariableTable`,
`sourfile`, сигнатуры вырезаны), а весь код пережёван (CFF, block-shuffle,
opaque-предикаты, invokedynamic-хлам, мёртвый код, шифрованные строки). Всё нужно
выводить **из семантики байткода**, а не из мета-данных.

## Главный принцип

Ничего не «читаем» — всё **выводим** из потока инструкций и CFG:

- имена/типы локальных — из dataflow-анализа store/load и позиций аргументов вызовов;
- контроль-флоу — из реальных переходов (порядок блоков в байткоде не важен);
- значения — из constant propagation;
- что недостижимо — выпиливаем после де-флаттенинга.

## Несущая архитектура пайплайна

```
JAR → ClassNode → CFG(BasicBlock) → CffUnflattenerPass → StructureRecoverer
     → StructureToAst → BytecodeToExpr → Ast → JavaPrinter
```

Критично для CFF-безопасности: **слои ортогональны**.

- Контрол-флоу (CFF/шаффл) разворачивается на **CFG-уровне**
  (`CfgBuilder`, `CffUnflattenerPass`, `StructureRecoverer`, доминаторы).
- Типы / boolean / invokedynamic / мёртвый код живут **ниже**, в эмиттере
  (`BytecodeToExpr`, `Ast`, `TypeInference`).
- Поэтому улучшения эмиттера **не влияют** на рековери структур.

**Запрет:** не сворачивать константы и не резать ветви ДО CFF-де-флаттенинга —
это единственное пересечение с контрол-флоу и было бы рискованно. Фолдинг
предикатов делаем в `StructureToAst` **после** развёртки.

## Якорь нерегресса (обязателен для каждого шага)

Любую доработку гоняем через эталоны; «CFF не тронут» = результаты не изменились:

- `cfftest-cff.jar` — классическая state-машина (`compute`, `branches`, `easy`, `gate`);
- `slashvisuals-test-obf.jar` — switch-gate / opaque-предикаты; современные прогоны —
  block-shuffle;
- `slashVV.jar` — обычная обфа;
- `cfr-0.152.jar` — без обфускации (эталон «не ломаем чистый код»).

Ожидание: `compute/branches/gate` не меняются, вердикты `--detect` те же.

## План по фазам (по убыванию ценности/надёжности)

### Фаза 1. Фундамент — усиленный вывод типов
- Специальная `BasicVerifier`/dataflow: тип слота = объединение по всем load/store
  + подстановка по позициям аргументов вызовов и операндам.
- От этого зависит всё: касты, boolean-локальные, generic, разбор arguments.
- Не трогает CFG — CFF-безопасно.

### Фаза 2. invokedynamic — строки и лямбды (самый заметный и автономный кусок)
- `StringConcatFactory.makeConcatWithConstants` → сцепление в `+`
  (сейчас выходит мусорный литерал `sp : Ljava/lang/String; ... [base64]`).
- `LambdaMetafactory` → `(…) -> …` / восстановление анонимных классов.
- Это инструкция в `BytecodeToExpr.consume`; на контроль-флоу не влияет.

### Фаза 3. Мёртвый код — отдельный pass
- constant propagation + unreachable-elimination **по CFG после де-флаттенинга**:
  резать нерабочие ветви и нереализуемые блоки, а не плодить их.
- Дополняет существующее: фолдинг opaque-предикатов, `terminated`-флаг,
  анти-тампер `try{}catch(Throwable){return;throw(0)}`.

### Фаза 4. Эмиттер до валидного Java
- `this`/`super()`/`this()`, настоящий `switch/case` (не CFF-диспетчер),
  `try/catch/finally` + multi-catch,
  чистить лишние касты и пустые блоки,
  генерировать объявления локальных по выведенным типам.

### Фаза 5. SSA-каскад упрощений
- на `SsaBuilder`: copy/constant propagation, убрать `iVar = x; iVar2 = y` цепочки
  и `return`-хвосты, склейка.

### Фаза 6. Имена без мета-данных
- идентификация «роль» локальных/аргументов по использованию (счётчик, флаг,
  коллекция, конвертер), по суперклассам/интерфейсам и по строкам — поверх
  `ClassRenamer`.

## Рекомендация по очерёдности

Начать с **Фазы 1 + 2** (типы + invokedynamic): они дают ~60–70% читаемости на
чистом байткоде и не зависят от остального. Затем **Фаза 3** (резать AD-объём),
потом **4–6**.

## Проверка на «адище»

Когда иишка докашеварит свой чудовищный вариант — прогон одним заходом:
`--detect` (вердикт), затем `--ast` (метрики: `throw(0)`, `/* ? */`, `.cast(Object)`,
`[][]`, `!= 0`, число ошибок классов, остатки неразвёрнутых тавтологий/switch/while,
пример проблемного метода). Каждый шаг плана пофазам закрывает конкретные дефекты,
найденные такой проверкой.
